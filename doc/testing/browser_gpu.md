# Browser GPU backend smoke procedure

**Status:** Procedure available; browser runtime results are pending. A successful
WASM build is not browser acceptance evidence. The repository does not currently
have an automated browser GPU test harness.

## Build and serve

From the repository root, build and serve the package as described in
[BUILD.md](../agents/BUILD.md):

```bash
wasm-pack build --target web --out-dir pkg --release -- --locked
python3 -m http.server 8000
```

Open `http://localhost:8000/static/index_image.html`. Use a fresh page load for
each backend selection; the real canvas cannot switch APIs after context creation.

## Create a small synthetic signed volume

On the page, open DevTools Console and run this snippet. It downloads an MHA
fixture with no patient metadata. The `MET_SHORT` voxels are signed little-endian
values generated by `-1024 + 128*x + 8*y + z` in a `16x16x8` volume.

```js
(() => {
  const [width, height, depth] = [16, 16, 8];
  const header = [
    "ObjectType = Image",
    "NDims = 3",
    "BinaryData = True",
    "BinaryDataByteOrderMSB = False",
    "CompressedData = False",
    "TransformMatrix = 1 0 0 0 1 0 0 0 1",
    "Offset = 0 0 0",
    "AnatomicalOrientation = HFS",
    "ElementSpacing = 1 1 1",
    `DimSize = ${width} ${height} ${depth}`,
    "ElementType = MET_SHORT",
    "ElementDataFile = LOCAL",
    "",
  ].join("\n");
  const voxels = new Uint8Array(width * height * depth * 2);
  const view = new DataView(voxels.buffer);
  for (let z = 0; z < depth; z++) {
    for (let y = 0; y < height; y++) {
      for (let x = 0; x < width; x++) {
        const index = x + width * (y + height * z);
        view.setInt16(index * 2, -1024 + 128 * x + 8 * y + z, true);
      }
    }
  }
  const url = URL.createObjectURL(new Blob([header, voxels], { type: "application/octet-stream" }));
  const link = document.createElement("a");
  link.href = url;
  link.download = "synthetic-signed-16x16x8.mha";
  link.click();
  setTimeout(() => URL.revokeObjectURL(url), 1000);
})();
```

Choose the downloaded file in **Input reconstruction file**, then click **View**.
The fixture's source values include `-1024` at `(0,0,0)`, `-256` at `(6,0,0)`,
`0` at `(8,0,0)`, `256` at `(10,0,0)`, `-1` at `(7,15,7)`, and `255` at
`(9,15,7)`. These are fixture invariants (including signed values and byte
boundaries), not measurements of GPU framebuffer pixels. The current browser
page does not expose a numerical GPU readback assertion; quantitative browser
image parity remains unverified.

## Backend and interaction checks

For each run, record browser and version, OS/GPU if available, startup backend,
selected volume encoding, reported 3D texture limit, console errors, and the
observed results. The startup log should include `Startup GPU summary` and `GPU
volume capabilities`.

1. **Automatic preference:** Open the page with no backend query on a browser
   where WebGPU is available. Confirm the selected backend is
   `BrowserWebGpu`; load the fixture and inspect the MPR views.
2. **Forced WebGL2:** Reload as
   `http://localhost:8000/static/index_image.html?kepler_wgpu_backend=gl`.
   Confirm the selected backend is `Gl`, then repeat the same fixture and
   interactions. Use a fresh page load when changing the query.
3. **WebGPU unavailable:** On a browser/profile where WebGPU is disabled or not
   supported, load with no query. Confirm the pre-canvas reason and selected
   `Gl` backend; then repeat the fixture checks.
4. Exercise transverse/coronal/sagittal and oblique MPR, MIP/MinIP/AvgIP, mesh,
   window/level, resize, pan/zoom/input, redraw after idle, and restoration after
   hiding/showing or resizing the tab/window. The controls on this demo page
   provide these paths. Check that the view remains responsive and no new
   validation errors appear. Run the same operations for automatic WebGPU and
   forced/fallback WebGL2. Do not infer backend parity from visual appearance
   alone; retain the fixture values above as data expectations.

## Startup, replacement, and lifecycle acceptance

For the wgpu/Winit upgrade, retain the existing `get_render_app` → `get_glcanvas`
→ enqueue volume → `run` sequence. Confirm construction resolves GPU-ready and
`run` returns normally to JavaScript. Repeat View/loading so the div-targeted
replacement canvas receives the supplied volume; exercise implemented async scalar,
coordinate, and rotation getters. Check getters/no-op controls leave a clean viewer
idle, animation stays bounded, hide/restore retains work, and quit stops callbacks.
The [migration guide](../rendering/wgpu30-migration.md) describes the bootstrap
bridge and fatal-fault restart behavior. These remain runtime checks, not claims
from packaging or source inspection.

## Controlled failure paths

These checks are also pending runtime evidence. For a controlled pre-canvas
WebGPU adapter failure, use DevTools before clicking **View** (the WASM app is
not started until then) to wrap `navigator.gpu.requestAdapter`: allow its first
call through so wgpu's availability probe succeeds, reject the next call with a
local test error, and then click **View**. Expect a stage-labeled WebGPU
preflight failure followed by a single GL candidate attempt and a final `Gl`
startup summary. Restore the original method or reload the page immediately
when done; do not ship the shim or retain a persistent browser override. If the
browser does not allow replacing that method, record the limitation rather than
claiming this path passed.

Also verify both-candidate exhaustion and post-binding diagnostics where a
controllable browser fault can be applied. The post-binding case must report the
selected backend and failed stage, advise a fresh-page forced-GL diagnostic, and
must not attempt another API on the already-bound canvas. Keep screenshots/logs
free of patient data; the fixture above contains none.
